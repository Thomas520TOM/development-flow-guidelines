# Coding Work Guidance

## Overview

This is a full development lifecycle guidance system, covering all stages from requirements analysis to post-deployment maintenance, testing, review, and security audit. Each stage has a corresponding rule file that is loaded on demand, rather than all being loaded at once.

This file serves as the usage guide for the entire system: it tells you when to invoke which module, how modules coordinate with each other, and how to collaborate across multiple conversations.

## Communication Tone

Regardless of which module is active, the AI's communication style remains consistent:

- **Teaching-oriented**: Explain the reasoning behind key decisions, but do not proactively start a lecture. Only dive deeper when the user asks.
- **Conversational, not bureaucratic**: Do not use templates or output formatted reports (unless the user requests them). Communicate as an experienced colleague would.
- **Present options, do not decide unilaterally**: When recommending solutions, present multiple options with their pros and cons, letting the user make the final call.
- **Respect thinking space**: Do not do everything for the user. Leave room for the user to add their own thoughts and adjustments.

## Instantiation Mechanism

This skill uses a template-instance architecture:

- **Template**: All rule files under the skill directory (SKILL.md + module rules) are shared templates across all projects and must not be modified.
- **Instance**: Each new project corresponds to an independent instance, containing that project's dedicated log files and records.

### Trigger Conditions

When the AI determines that the user has started a new project (typical signal: the user describes an idea that has not appeared before), it should create an instance for the new project:

1. Determine the instance directory (suggested: `C:\Users\<username>\Documents\Codex\instances\<project-name>\` or the project root directory)
2. Create log files in the instance directory (using files from the asset template `assets/instance-template/` as seeds)
3. After the instance is created, all log write operations should target files in the instance directory

### Continuation of Existing Projects

When the user says "continue with the last project" or expresses similar intent:

1. Load log files from the instance directory to restore context
2. If a context snapshot exists, present a concise restoration summary
3. Enter the corresponding module based on the last active stage recorded in the logs
4. Do not create a new instance, and do not modify template files

### Isolation Between Template and Instance

- The AI must not modify any rule files under the skill template directory
- All dynamic data generated by projects (logs, records, etc.) is written only to the instance directory
- The template ensures consistent rules and initial state when starting a new project each time

## Intent Inference and Stage Identification

### Identification Principles

Users do not explicitly announce stage transitions. The AI should infer the user's current stage and intent from the **natural semantics of the conversation**, rather than waiting for the user to name a module.

Inference basis includes:

- **What the user is currently discussing**: Talking about ideas, discussing solutions, asking about technical details, or directly writing code?
- **Conversation context**: What was being discussed earlier? Has there been a clear topic shift?
- **User's existing outputs**: What stages have already been completed according to the log files?
- **Project state**: Is this a new project or modifications to existing code?
- **Conversation length**: Has the conversation exceeded 20 turns? (Trigger context management)

### Typical Signal Reference

Below are common scenario-based inference guidelines, not exhaustive. The AI should judge flexibly based on actual conversation:

- User describes a vague idea, "want to build a XX", "have a requirement", "something like this..."
    → Infer being in the requirements analysis stage

- User discusses technology choices, "what framework to use", "how to store data", "how to structure the project"
    → Infer being in the technical structure design stage

- User asks "how to implement this", "what's the best approach", "how to use this library"
    → Infer needing the skill guidance dictionary

- User says "help me write one", "implement this", "is the code like this"
    → Infer entering the code generation stage
    → Before writing code, run the testing strategy module to define test plans

- User says "there's a bug", "this feature has a problem", "help me see what's wrong"
    → Infer entering the post-deployment maintenance stage

- User says "what do you think", "are there any issues", "review this code"
    → Infer needing the evaluation system or code review module

- User says "check my code", "any security issues", "audit this"
    → Infer needing the code review module and potentially the security review module

- User says "what's the status", "where are we", "what's left", "how much is done"
    → Infer needing the progress tracking module

- User mentions "lost context", "what were we doing", conversation restarts after many turns
    → Infer needing the context management module to restore state

- User says "it failed", "something went wrong", "continue from where we stopped"
    → Infer needing the error recovery module

### Transition Detection

Users may naturally transition from requirements analysis to technical design, and from design to code generation within the same conversation. The AI should be perceptive to such topic shifts:

- When transitioning from one stage to another, there is no need to inform the user "now switching to X module"; simply follow the rules of the new stage directly
- Transition signals include: changes in question type, shifting from "what I want" to "how to implement", moving from discussing solutions to writing code
- If the AI is uncertain about the current stage, it should prefer to continue following the previous stage's rules rather than switching frequently

### Behavior When Uncertain

If the AI cannot determine the user's current intent, the default behavior is:

- New conversation with no existing logs → default to starting from requirements analysis, proactively guiding the user to describe their idea
- Existing project with logs → read the logs and continue from the last active stage recorded
- If the user directly requests code and requirements are clear → enter code generation directly, without rigidly going through preceding stages

## Inter-Module Workflow

### Standard Flow

Full project lifecycle; testing, review, and evaluation can be triggered at any stage:

```
User has an idea
    │
    ▼
Requirements Analysis ──Output: module list + boundaries + blind spots
    │  (optional → evaluation system reviews requirements analysis)
    ▼
Technical Structure Design ──Output: architecture diagram + function list + data flow + blind spot plan
    │  (optional → detour to skill dictionary: slice to learn / optional → evaluation system reviews design)
    ▼
Skill Guidance Dictionary (on demand) ──Output: solution explanation + examples
    │
    ▼
Testing Strategy ──Output: test plan per feature unit
    │  (gate: no implementation code until test plan is defined)
    ▼
Code Generation ──Output: runnable code with passing tests
    │  (optional → evaluation system reviews code)
    │
    ▼
Code Review ──Output: severity-ordered findings report
    │  (optional → security review for sensitive code)
    ▼
Post-Deployment Maintenance (triggered on demand, optional → evaluation system reviews modification plan)
```

### Quality Gate Sequence

After code generation, the following gates must be passed (in order) before considering work complete:

1. **Testing Strategy**: Tests exist, pass, and cover the new behavior
2. **Code Review**: No critical or high issues remain unresolved
3. **Security Review** (if applicable): No exploitable vulnerabilities present
4. **Evaluation**: Feedback incorporated or explicitly deferred

### Non-Standard Flow

Users may use the system out of order:

- Write code directly: skip preceding stages, enter code generation directly (testing strategy still applies as gate)
- Mid-session learning: encounter something unknown during code generation, switch to the skill dictionary to learn, then return
- Review at any time: request feedback at any point, enter evaluation or code review directly
- Fix things only: existing project has issues, enter post-deployment maintenance directly
- Audit-only: run security review on existing code without other stages

### Multi-Conversation Collaboration

The skill guidance dictionary and code generation should in principle be conducted in separate conversations:

- Dictionary conversation: learn solutions, understand principles, discuss choices
- Code conversation: after settling on a solution, open a separate conversation to write code

Other modules can proceed consecutively within the same conversation. Context management auto-summarizes when conversations exceed 20 turns to maintain continuity.

### System-Wide Modules

These modules operate across stage boundaries:

- **Context Management**: Auto-summarizes at 20+ turns, persists key decisions, restores state on new conversations.
- **Error Recovery**: Sets checkpoints, detects breakpoints on resume, handles graceful degradation.
- **Progress Tracking**: Maintains completion state, reports progress at milestones and on request.
- **Extension Interface**: Defines the contract for custom module registration and inter-module communication.

### Log System Integration with Other Modules

The log system is written to or read at the following moments:

- Module transitions: AI silently appends to logs (requirements → architecture → implementation)
- New conversation begins: AI reads existing logs to restore context
- Maintenance begins: AI reads logs to understand project background
- Evaluation system runs: AI reads logs to track previous critique points
- Testing strategy runs: Test plans and coverage results are logged
- Code review completes: Review findings summary is logged
- Security review completes: Security findings and resolutions are logged
- Error recovery activates: Checkpoint markers and recovery actions are logged
- Progress tracking updates: Progress snapshots are written to the implementation log
